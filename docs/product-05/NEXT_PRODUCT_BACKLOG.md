# PRODUCT-05 — next product milestones (proposal; replaces the PRODUCT-04 list)

Done by PRODUCT-05: a read-only review queue ("İncelenmesi Gerekenler") on the Projects page and a Dashboard summary, from one pure derivation, with honest loading / failed / old / uncertain states and a navigation-only "Matriste incele". Still **not** proposed: real installation, the jq pilot, any change to pilot gates or Smart App Control handling, the deferred offline-preflight harness (it is not revived by this list), signing / auto-update, cloud sync. Real installation stays behind its own acceptance gate (Issues #14 and #25 open, independent Red Team, separate explicit instruction). No secrets or private paths belong in this file.

| # | Milestone | Measurable user value | Prerequisites (state today) |
|---|---|---|---|
| 1 | **Observation provenance in the contract (Rust, additive).** `RequestVsObservation` says whether its status rests on a project-specific, computer-wide or `local-cli` observation, and carries the age of the evidence. | The matrix and the queue stop saying "may count for every project" and say which it is; `present_current` can be worded precisely. | Small additive field in `store.rs` + type + one line of UI. Its own reviewed phase. |
| 2 | **Evaluation-log hygiene (Rust).** A UI-discarded evaluation must not consume the "already shown for this task" slot, or a read-only dry-run evaluation is exposed. | No suggestion is "used up" by an answer nobody saw; the fresh-task-id workaround can go. | `recommend.rs` / `commands.rs`. Should precede anything that evaluates more often than the user clicks. |
| 3 | **Durable "reviewed" state — only with a data model.** An explicit, reversible acknowledgement per exact key + reason + the fact it was acknowledged against (e.g. the catalog revision or the scan id), so a new change re-opens the item. | The queue can reach "nothing new" honestly. Today it deliberately cannot be cleared by looking. | A migration, a typed command, a security review and explicit approval. **Not** a UI-only flag. |
| 4 | **Per-project plan export (read-only, user-consented).** Markdown/JSON "desired toolchain" that states *wish* and *last stored observation* separately and never says "installed". | A plan can be handed to a teammate. | First user-driven file write: typed command, user-chosen location, review. |
| 5 | **Transparent suggestion overlay (after the rule audit).** Show the deterministic rule result for a typed task as a mark on matrix rows, through the typed handoff, no new storage. | From a task description to the relevant undecided tools without a second screen. | The rule set has **not** been audited; do not build before that. |
| 6 | **Targeted UX visual review.** A human pass (screen reader, keyboard, high-zoom, dark theme) over the queue, the matrix rows and the observation block, plus an editorial review of the Turkish copy. | The new surfaces are checked in a real window — something jsdom cannot show. | Needs a person with the app open; not an automated phase. |

## Order and why
1 first: it removes the largest remaining ambiguity in what the stored status means. 2 is the other Rust fix and a precondition for more evaluation. 3 only after 1 (an acknowledgement should be bound to a precise fact). 4 is the first user-driven write of its kind. 5 waits for the rule audit. 6 can happen at any time and does not depend on code.
