## 2. The attestation (SLSA provenance, Sigstore)

`tools/verify_sigstore_bundle.py` verified, **offline against the Sigstore trusted root**, one bundle that covers **27 release files** (including both targets) with 28 checks each for the Windows and the macOS subject — all passed (`evidence/report-*.json`):

* **V** DSSE envelope signature with the leaf certificate key; the certificate chains (3 certificates) to a Sigstore public-good Fulcio CA that was valid at the log time; the leaf was valid for 10 minutes (14:10:23–14:20:23Z) and the log time (14:10:23Z) is inside it.
* **V** Certificate identity: SAN `https://github.com/jqlang/jq/.github/workflows/ci.yml@refs/tags/jq-1.8.2`; OIDC issuer `https://token.actions.githubusercontent.com`; source repository `https://github.com/jqlang/jq`, ref `refs/tags/jq-1.8.2`, digest = commit `34f7186b…`; build signer digest = same commit; repository id 5101141; owner id 104800540; trigger `push`; runner `github-hosted`; run `https://github.com/jqlang/jq/actions/runs/27872779544/attempts/1`.
* **V** Transparency log (Rekor, log index 1884519155): log id is the trusted-root log, signed entry timestamp verifies, the RFC 6962/9162 inclusion proof reproduces the signed root, the signed checkpoint verifies, the logged entry is this very envelope.
* **V** In-toto statement v1 with SLSA provenance v1: `jq-windows-amd64.exe` → `a6fc67fe…c627`, `jq-macos-arm64` → `2d75340b…ca07e`; workflow repository/path/ref and resolved dependency `gitCommit` as above.
* Negative tests (`tests/test_phase3d0_contract.py`) show the verifier is not vacuous: a wrong digest, name, ref, commit, repository or workflow, and any flip of the payload, signature, certificate, log time, log index, SET, proof hash, root hash or log body, and a trusted root without CAs or without the log, are all rejected.

**Trust root.** The Sigstore public-good instance (Fulcio CA + Rekor v1 log key), obtained through the GitHub CLI's TUF-verified embedded root (`gh attestation trusted-root`); the stored snapshot is evidence only and must be refreshed by a later reviewer. GitHub's OIDC issuer vouches for "this workflow run, in this repository, at this commit".

**Verification identity policy** (to be enforced by any verifier, here and in a later phase): exactly repository `jqlang/jq` (id 5101141), workflow `.github/workflows/ci.yml`, ref `refs/tags/jq-1.8.2`, commit `34f7186b86743a083a589741b6cea95293524108`, issuer `https://token.actions.githubusercontent.com`, GitHub-hosted runner, subject name and SHA-256 exactly as above. A different workflow, ref or commit is a failure, not a warning.

**Digest scope.** The subject is the digest of the **exact file** that would be installed (raw executable) — it matches the recipe scope `exact_file`; no archive or extraction step is involved.

**What the attestation does not say.** That the source or the build was benign; that the workflow itself was unmodified before the tag (the tag points at a Dependabot merge and the workflow uses tag-referenced, not SHA-pinned, third-party actions such as `actions/checkout@v7`, `msys2/setup-msys2@v2` with `update: true`, `actions/attest@v4`); that the build is reproducible (the Windows build pulls a rolling MSYS2 toolchain); and — most importantly — that **the file you hold** has that digest, which can only be checked on downloaded bytes (`--artifact`). Not done here.

## 3. The second, independent-looking channel: publisher GPG signatures

The release job also signs every release file with a GPG key and commits the detached signatures and `sha256sum.txt` to the repository through a pull request (`sig/v1.8.2/*.asc`, commit "Update signatures of 1.8.2 (#3566)", signed by GitHub web-flow). Findings (**V** for the metadata, **U** for the signature validity, which needs the bytes):

* **Pinned retrieval (Phase 3D-0 closure):** the signatures, the checksum list and the key are addressed by the immutable commit `f0dabad36a5fdb37393829e6bd4c465d70c40a3a` ("Update signatures of 1.8.2 (#3566)", parent = the release commit, committed by GitHub, pull request approved and merged by maintainer `itchyny` two minutes after the bot opened it), never by `master`; their SHA-256 values and git blob ids are recorded in `evidence/pinned-f0dabad…/` and in `tools/review_jq_verification.py`; the master blobs were identical on 2026-10-18.
* Signing key: `jq Release Signing Key <no-send-email@jqlang.github.io>`, RSA 4096, created 2025-07-31, fingerprint `9307 9A95 11EF C0B7 D6CD BFB5 B0DA 60FB 454B AF18` (`sig/jq-release-new.key`). The signature packets of `jq-windows-amd64.exe.asc` and `jq-macos-arm64.asc` name this key, created 2026-06-20.
* **Weakness to state plainly:** the previous "new" key expired on 2025-07-26 (issue <https://github.com/jqlang/jq/issues/3381>); the project then created this key **on 2025-07-31 and re-signed 1.7.1, 1.8.0 and 1.8.1 with it the same day**. Key continuity therefore gives no independent history, and the website (<https://jqlang.org/download/>) **lists no fingerprint** and does not mention attestations. The only anchor of the fingerprint is the repository itself — same origin as the artifacts. A reviewer pins the fingerprint above (exact match required) in the reference entry, so a later silent key swap is noticed, but this is a consistency check, not an independent root.
* The signing step runs in the same job that holds the OIDC token, so an attacker who controls that workflow controls both channels. Their value is defence in depth against a narrower attacker (one who can alter release assets but not run the release job).

## 4. Revocation, replay and downgrade

* **No revocation channel.** An attestation or signature never expires; GitHub can delete an attestation, the maintainers can withdraw a release, but no client learns of it unless it asks. In the manager, revocation is "remove the reference entry in an application update"; devices that are not updated keep trusting the old entry (disclosed in Phase 3B).
* **Mutable release** (`immutable:false`, upload with `--clobber`): assets can be replaced after publication. The pinned exact-file digest protects against a replaced asset; it does not protect against a *replacement that is itself freshly attested*, which is why the identity policy pins the exact ref and commit.
* **Downgrade/replay:** an old, validly attested and signed version cannot satisfy a pinned digest of 1.8.2; the recipe and approval name the exact version and digest. Older versions are vulnerable: `GET /repos/jqlang/jq/security-advisories` lists 27 published advisories; 20 of them list `<= 1.8.1` with 1.8.2 as the patched version (three high severity, memory-safety and complexity issues published April–June 2026); the other 7 list older versions (1.7.x, 1.8.0, `< 1.8.0`, `master` at the time, or an Oniguruma issue for `<= 1.8.0`) and 5 of those carry no 'patched' field — the metadata does not say whether they affect 1.8.2, so this is **not** a claim that 1.8.2 is free of known issues. No advisory affecting 1.8.2 was listed on 2026-10-18, and 1.8.2 is the newest release. The advisory rate is high: **installing without executing is a different risk class from running it** (separate permission, not requested).

## 5. Licence and bundled notices

* GitHub's licence API says `NOASSERTION` because the repository carries several licences. `COPYING` at the tag: jq itself **MIT** (copyright 2012 Stephen Dolan); documentation (`docs/`, not part of a binary) CC BY 3.0; David M. Gay's `dtoa.c`/`g_fmt.c` (Lucent permissive notice, binary distribution requires keeping it); `decNumber` under the **ICU** licence; Heimdal-derived code (BSD 3-clause style); a modified NetBSD `strptime` (BSD 2-clause style).
* **Gap:** the binaries are statically linked with the vendored Oniguruma (`vendor/oniguruma`, submodule commit `4ef89209a239c1aea328cf13c05a2807e5c146d1`; upstream licence is a BSD-2-clause-style text, `NOASSERTION` in the API) and, for Windows, with MSYS2/UCRT64 runtime pieces (permissive licences, **not** recorded in `COPYING`). The notices the *binary* actually requires are therefore not fully listed by jq's own `COPYING`. The manager would not redistribute the file (it fetches the publisher's release at install time), but a licence/notice record for the installed tool is a **human decision** that this phase does not make. Required before an install: owner review of `COPYING` at the tag + the Oniguruma licence + a decision what is shown at approval time and stored next to the installed file.

## 6. Smart App Control and Gatekeeper

* **Windows.** The workflow has **no code-signing step** (no `signtool`, no certificate secret): `jq-windows-amd64.exe` is built with MSYS2 GCC and uploaded as is. It is therefore expected to be **unsigned (Authenticode `NotSigned`)** — **U**, to be confirmed read-only on the bytes. On a machine with Smart App Control in enforcement mode, an unsigned, low-reputation executable may be blocked **when first launched** (the same behaviour the project already sees for its own freshly built test executables, see `PHASE-3D0.md` §6). Installing (writing) the file is not blocked by SAC; executing it may be. The manager must not and will not change SAC/Defender; the honest outcome is "installed, may not run on this machine".
* **macOS.** The workflow has **no `codesign`/notarisation step** either; the arm64 binary is linked on `macos-14` and stripped (`strip ./jq`). Apple Silicon requires at least an ad-hoc signature to execute; whether the stripped, linker-signed output carries a valid one is **U** (checked read-only on a real Mac with `codesign -dv`/`-vv` after a separately authorised download). Gatekeeper's assessment applies to quarantined files; a file written by the manager has no quarantine attribute unless the manager sets one, which it must not strip or add silently. Notarisation will not be present.

## 7. Verdict

A practical, defensible provenance route **exists**: the reviewer verifies the attestation (done at statement level here, 28 checks), then — after a separately authorised download — hashes the two exact files, requires digest = attestation subject = release digest = `sha256sum.txt`, verifies the GPG detached signatures with an isolated keyring and the pinned fingerprint, re-verifies the attestation with the GitHub CLI as a second implementation, and only then proposes a reference entry. Until those bytes exist, **nothing is entered in the authenticated-reference set**, `identity_verified` keeps its meaning, and no digest is created from release metadata. Residual risks to disclose: upstream repository/workflow compromise, mutable tag-pinned actions and rolling toolchain at build time, unsigned binaries, no revocation, high vulnerability rate, incomplete notices.
