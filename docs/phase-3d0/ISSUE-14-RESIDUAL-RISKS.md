# Issue #14 — the two remaining filesystem windows: decision record (Phase 3D-0)

**Issue #14 stays open.** Green CI does not close it. This document analyses the two windows named in Phase 3C, decides what is acceptable for a *first* pilot, and lists the tests and real-device evidence that are still required. No filesystem abstraction was rewritten.

Common facts: the managed root is an owner-only folder created by the manager (`atm-managed/root-<id>`); every name inside it is manager-defined (ASCII `[A-Za-z0-9._+-]`, validated); user data lives in `data/<tool>` and is **never opened** by the adapter; the application database and the application binary are writable by the same user and are therefore *out of scope* of this threat model (a process with the user's rights can already rewrite them).

## A. Windows — a destination swapped in the gap before a replacement

| Aspect | Analysis |
| --- | --- |
| Where | `Dir::replace_owned_file` on Windows (`managed_fs_windows.rs::rename_file`, `Mode::Replace`): the destination's identity and link count are checked through an open handle, then `FileRenameInformationEx` replaces whatever the *name* designates at that instant. |
| Attacker / precondition | A process running **as the same Windows user** that, within the interval between those two calls (microseconds), deletes the verified destination and creates a different file under the same name. No other user can do this (owner-only DACL); no administrator is needed or assumed. Tried and rejected: pinning the destination with a handle that forbids delete sharing — Windows then refuses the replacing rename itself (sharing violation, tested). |
| Names affected | Exactly three, all transaction-owned: `journal/<txn>.json` (every journal write), `state/<tool>.json` (the active pointer: update switch and rollback restore). |
| Can ordinary activity trigger it? | No realistic case: anti-virus scanners, indexers and cloud-sync clients open files, they do not delete and recreate manager-internal names in that interval. A program that recreates its own file at that name is not conceivable (the names are the manager's). |
| Can it destroy unrelated data? | **No.** The overwritten object is whatever the same-user attacker placed under a manager-internal name inside the managed root. A hard link to a user's file would lose only the extra *name*; the user's data is untouched. `data/` is never opened. Worst consequences: a journal or pointer the manager wrote is replaced by attacker-chosen JSON. A forged pointer can only name a `<tool>/<version>` folder below the managed root (names are validated), so it cannot point outside. |
| Which primitives would reduce it | (1) *Never replace*: write numbered generations (`state/<tool>.<n>.json`, `journal/<txn>.<n>.json`) with the existing atomic no-clobber create, choose the highest valid generation on read, delete superseded generations by verified handle. Eliminates the window; changes the on-disk shape and every reader. (2) *Detach-then-create*: delete the verified destination by its handle (POSIX semantics, so the object deleted is exactly the verified one), then no-clobber-create the new file; a newcomer in the gap makes the create fail instead of being overwritten. Costs atomicity (a crash between the two steps leaves **no** file); acceptable for the pointer (the snapshot restores it), not for the journal. (3) Oplocks: only notify. |
| Conservative fail-closed workaround available now | None needed for correctness: the next step after a replacement is always to read back (the pointer is re-read by `active_version`; the journal is re-read at recovery with a digest), and any inconsistency fails closed (`NeedsAttention`). For a stricter first pilot the pointer can move to option (2) without touching the journal. |
| Tests | Existing: `a_destination_swapped_in_the_gap_before_a_replacement_is_not_clobbered_where_the_platform_can_tell` (records the window on Windows, asserts refusal on macOS), `a_pointer_swapped_for_another_file_before_the_switch_is_never_replaced`, `a_journal_that_was_replaced_by_another_file_is_never_overwritten_by_the_next_save`. Required on real devices: the acceptance probe (below). |
| Residual risk after mitigation | Same-user attacker, microsecond window, effect limited to manager-internal control files inside the owner-only root, detected at the next read. **Decision proposed: accept and disclose for the first pilot; take option (2) for the pointer if the Red Team asks for zero-clobber on Windows.** |

## B. macOS — the unlink window

| Aspect | Analysis |
| --- | --- |
| Where | `Dir::remove_file_verified` on macOS: the file is opened with `O_NOFOLLOW`, identity/links/size/SHA-256 are checked on the descriptor, `fstatat` on the *name* must show the same `(dev, ino)`, then `unlinkat`. macOS has no "unlink exactly this inode". |
| Attacker / precondition | A process running **as the same macOS user** that, between the final `fstatat` and `unlinkat` (microseconds), replaces the verified name by another object. |
| Names affected | Any file the manager deletes by name: staged and moved artifacts during rollback/cleanup/uninstall, snapshot files, lock and journal-adjacent files. |
| Ordinary activity? | Not realistically (Spotlight, Time Machine, antivirus do not rename or recreate manager-internal files in that interval). |
| Unrelated data destroyed? | **No.** `unlinkat(…, 0)` removes a *directory entry*. If the newcomer is a symlink, the link is removed, not its target; if it is a hard link to a user's file, only that extra name disappears and the user's inode survives through its other name; a directory fails (`EPERM`/`EISDIR`). The managed root is owner-only. The worst outcome is the loss of an attacker-placed (or attacker-swapped) entry inside the managed root. |
| Primitives that reduce it | (1) *Rename-to-quarantine then unlink*: `renameatx_np(RENAME_EXCL)` the verified name into a manager-owned `trash/` folder, **re-verify the identity at the new location**, then unlink there; if the re-verification fails the object is moved back with `RENAME_EXCL`. After the rename the manager unlinks only an object it has just verified in a place the attacker cannot swap into. The cost: if the swap happened *before* the rename, a foreign object is briefly relocated inside the managed root. (2) APFS-only calls (`clonefile`, `fcntl` path-by-fd) do not provide inode-unlink either. |
| Fail-closed workaround | Option (1) is the narrow fix if wanted; it needs one more managed folder and one more journalled intent (`trash`). Not implemented now: it would add a new moving part to every deletion for a window whose damage is bounded as above. |
| Volume differences | `RENAME_EXCL`/`RENAME_SWAP` are "only on file systems that support" them (macOS `rename(2)`; queryable with `getattrlist(2)`, `ENOTSUP` otherwise). **Preserved as unsupported:** `ManagedRoot::establish`/`open` now run `Dir::probe_atomic_rename` (scratch files in `staging/`, removed afterwards) and refuse a volume on which the no-clobber move or the replacement does not work (`Unsupported`); nothing falls back to `renameat`. External or network volumes are expected to be refused (network file systems already are, at the anchor). |
| Tests | Existing barrier tests (`a_source_swapped_in_the_gap…`, `a_swap_between_the_check_and_the_deletion_never_deletes_the_newcomer`) run in macOS CI; new: `a_volume_without_the_atomic_primitives_is_refused_and_nothing_is_left_behind`, `the_capability_probe_proves_the_volume_and_leaves_nothing…`. Required on a real Mac: the acceptance probe on the internal APFS volume and on an external volume. |
| Residual risk | Same-user attacker, microsecond window, bounded to manager-internal names. **Decision proposed: accept and disclose for the first pilot; implement option (1) only if the Red Team requires it.** |

## C. What closes Issue #14 (not done)

1. The acceptance probe (`fsAcceptanceProbe` in `--self-check`) run and recorded on: the existing Windows 11 development PC (done in this phase), a **second Windows computer**, and a **real Apple Silicon Mac** — internal volume and one external volume.
2. The Windows `held folder` and `open file` observations reproduced on those devices (they depend on anti-virus and file-system filters).
3. A written decision by the Red Team on the two disclosed windows (accept, or take option (2) / option (1)).
4. A real mount transition test (macOS disk image mounted below a managed sub-folder; Windows volume mount point) — currently only simulated.
