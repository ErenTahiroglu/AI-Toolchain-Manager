# End-to-end evidence in the real application window (Phase 3D-3)

**What was run.** `tools/gui_install_flow.ps1` started the **real application window** — a debug build made with `--features synthetic-pilot` (never the release build; executable SHA-256 `a5008d35676c4468aa754a2259b20b0c7528574d01fdd31337a82940ce9d6eda`, built from the source of this commit before the documents and evidence files were added) — with an **isolated data directory** and drove it through the WebView2 debugging port on `127.0.0.1` with `tools/gui_install_flow.mjs`. After each step the file system of the isolated directory was inspected (`tools/fs_inventory.mjs`). Only **synthetic tools and bytes** were involved; nothing installed was executed; no network, no Windows Hello, no jq. No Smart App Control block occurred for this binary.

**Result: 74/74 checks true in phase `first`, 6/6 in phase `after-restart`** (the first process is killed, not closed). Raw results: [`first-result.json`](evidence/gui/first-result.json), [`after-restart-result.json`](evidence/gui/after-restart-result.json). All 46 audit rows of the run validate against the Phase 0 audit-event schema (0 violations).

The Phase 3D-2 scenarios (statuses, preview, forged IPC, cancel, install, replay, details, removal with user data, reinstall, tamper, restart) all still pass — see [the earlier record](../phase-3d2/GUI-EVIDENCE.md). New in this phase:

## What this does not show

jq, a real executable, how Smart App Control reacts to executing or even writing a real `.exe`, a second computer, macOS, a mid-transaction crash of the window process (crashes are injected in the Rust tests at 13 points), a real disk-full or access-denied condition (simulated in tests; a held-open file is exercised on Windows).
