# Phase 3A — Reviewed recipe foundation and synthetic transactional lifecycle

Baseline `d8a1389012e806469d1e47b5e64f5fbb8639dfdd` (accepted Phase 2D closure; Red Team Issue #12). **No real tool is installed, downloaded, started, updated or removed.** The transactional engine exists to prove that a lifecycle can be done honestly — and it can only touch isolated, synthetic test directories. It is not wired to any command, button or IPC function. The compiled-in recipe list and the authenticated reference set are both **empty**; every real catalog entry stays unapproved.

## 1. Issue #12 — positive evidence needs the same provenance as negative evidence

* **Root cause.** Only *absence* required `latest_scan_checked && scan_looked`; *presence* relied on the stored `current` flag alone, and the store derived `current = true` for a latest-scan row even when that scan had no permission for the row's area.
* **Fix, in two layers.**
  1. `discovery::store::reason_not_current`: a row that claims to come from the latest scan for an area that scan was not allowed to look at is **not current** ("inconsistent record, treated as untrusted"). The record itself is kept, not rewritten.
  2. `plan.rs`: one rule, `provenance_ok` = current ∧ from the latest scan ∧ `latest_scan_checked` ∧ the scan's own permission flags agree — for presence, absence and the settings-file prerequisite alike. A row that says `current` but fails it is counted as `inconsistent` and surfaced as the warning `inconsistent_observation_ignored`; it is never evidence.
* **Project alias.** `plan_for` (and `approve`/`verify_approval`) require the alias to name a registered, not removed project (`projects::is_registered`); a well-formed unknown alias, a path-like string, a missing alias and a removed project are all refused.
* **Tests.** Current-present + `scan_authorized_path = false`; + `latest_scan_checked = false`; + provenance `earlier_scan`; + wrong scope, surface or platform; settings records needing the user-config / project permission; a database whose latest scan row is edited to lack the path permission (record kept, `current` false); unregistered / removed project aliases. Mutation: `provenance_ok = current` fails three tests.

## 2. The reviewed recipe registry (`recipe.rs`, `schemas/reviewed-recipe.schema.json`)

A recipe is the typed, versioned statement of *exactly* what installing one tool version on one target does: tool id, **exact** version, platform + agent surface + scope, immutable source (exact 40/64 lower-case hex commit + whether it is *attested*), the artifact (file name, size, SHA-256, **digest scope = exact file**, canonical format), authentication evidence, license review, permissions, filesystem changes (closed areas), network destinations (closed), lifecycle actions, the four typed install operations (fetch → verify → stage → activate, each schema-valid per `install-recipe.schema.json` and bound to this artifact's digest), and a **rollback contract** (`designed` | `simulated`; what it undoes, what it never undoes — `tool_user_data` must be named). The review (`draft | reviewed | rejected`, reviewer, staging evidence, **the digest of the content that was reviewed**) is a separate record; **approval is not part of a recipe at all**.

Trust model, enforced by `recipe::problems`:

* **Untrusted metadata never becomes a recipe.** Nothing is derived from the catalog, a README or a typed command. A catalog record carrying an `installRecipe` blob changes nothing (tested).
* **Independent authentication of the artifact digest:** it must equal an entry of the *authenticated* reference set for this tool, version, platform, exact-file kind and verified format (the Phase 2C machinery); an unauthenticated reference, another version/platform/format/kind, or two conflicting authenticated references fail. An archive digest scope is refused. The production authenticated set is empty, so no real recipe can validate.
* **Review is bound to content:** any edit after review → `changed_after_review`. A draft/rejected review, a missing/failed/non-independent staging check, a non-accepted license, `verified` rollback (needs a real target), inexact versions (`latest`, ranges), unknown permissions/areas/destinations, a step list that is not the exact template, and an inconsistent `synthetic` flag are all separate refusals.
* **Source attestation** can only be claimed by a synthetic recipe through synthetic evidence. A real recipe's plan therefore keeps `source_origin_unverified`.
* `RecipeRegistry::production()` is the empty compiled-in list; `RecipeRegistry::synthetic()` refuses anything not marked synthetic with a `synthetic-` tool id.

### Plans and recipes

`build_plan_with` overlays a **validated, exactly matching** recipe on the catalog-derived draft: it replaces the recipe-derived blockers with a single new one, `user_approval_missing`, fills in the four typed steps, permissions, destinations, uninstall and rollback text and sets `recipe.state = validated`. Everything catalog-side that a recipe must not override stays (removed/quarantined/blocked entries, unsupported combinations, unsupported host, a different computer platform, unverified prerequisites, unknown agent session). The plan stays `preview_only`, `blocked`, `executable = false`, and carries `approvalState = "not_given"`; `parse_plan` rejects any plan that says otherwise. An invalid recipe leaves `no_approved_recipe` and lists closed problem codes; two candidates are `ambiguous_recipes`; a recipe for another question is `recipe_does_not_match_the_question`.

## 3. The approval contract (`approval.rs`)

An approval is a **separate object** created by one explicit user action. It binds: recipe id + revision + **digest**, the plan id, tool + exact version, platform + surface + scope + (for project scope) a **registered** project alias, the computer, the permissions digest (permissions + filesystem changes + network), a digest of the material prerequisites (their states, evidence basis, conflicts and blocker codes), the lifecycle action (`update` also its source version), the actor, `approvedAt` / `expiresAt` (≤ 24 h; 15 min default) and a SHA-256 binding over all of it. `verify_approval` judges it against *what is true now* and names the first thing that changed: `binding_mismatch`, `actor_not_allowed`, `expired` / `not_yet_valid` / `bad_lifetime`, `recipe_changed`, `action_changed`, `wrong_computer`, `target_changed`, `project_unknown`, `plan_blocked`, `permissions_changed`, `prerequisites_changed`, `plan_changed`.

* The confirmation is a typed text bound to action, tool, version and platform; a confirmation for something else is refused.
* **A plan id / SHA-256 is not an authorization**; the binding is tamper *evidence*, not a signature. The only consumer, the synthetic engine, accepts nothing but a `VerifiedApproval` produced by `verify_approval`.
* **Only synthetic test actors exist.** The production policy (`ApprovalPolicy::production()`) accepts no actor at all, and no user-interface control creates an approval.
* The engine re-checks authority itself and the expiry again immediately before the first change to managed state.

## 4. The synthetic transaction engine (`lifecycle.rs`)

* **Sandbox.** `SandboxRoot::create(base, computer_id)` makes a *new* folder `atm-synthetic-<uuid>` with a marker file; it never adopts an existing folder, refuses a base that is a file or a link, and `open` refuses anything without the marker, with another name pattern, that is a link, or whose layout (`staging versions state journal receipts snapshots locks data`) is damaged or redirected. Every path is `root/<fixed top folder>/<validated components…>`; a component is ASCII `[A-Za-z0-9._+-]`, ≤ 64, no `..`, no Windows device names; every path element is checked not to be a link/junction before use. No caller names a destination.
* **Authority.** A `ValidatedRecipe` marked synthetic with a `synthetic-` tool id plus a `VerifiedApproval` bound to that recipe digest, tool, version, computer, platform and action, inside its lifetime.
* **Identity of the artifact.** The artifact is a byte buffer given by the caller (never downloaded). Its size and SHA-256 must equal the recipe's, its format (sniffed from the bytes) must equal the recipe's, and `reference::evaluate` against the authenticated reference set must say `matches_authenticated` for this platform and version.
* **Flow** (typed operations only; no command runner): lock (`create_new`) → write-ahead journal → snapshot of the managed state (pointer) → stage into `staging/<txn>/` → verify the staged bytes → freshness check → create `versions/<tool>/<version>/` → **one atomic pointer switch** (`state/<tool>.json` via temp + fsync + rename) → durable receipt → journal `committed` → cleanup. Intents are written to the journal *before* the effect they describe.
* **Update** keeps the previous version folder; **uninstall** moves the pointer and the version folders into the transaction snapshot (so they can be put back), commits, then discards them — the tool's own `data/<tool>` is **never** touched and the receipt says `kept: user_data`.
* **Idempotency.** An install/update that already holds (same version, same digest, valid receipt) returns the existing receipt and changes nothing; an uninstall of something not installed is refused as a no-op; a stale lock or an unfinished journal blocks new work (`Busy` / `Pending`) *before* the installed state is consulted. Two transactions for one tool cannot run at once; different tools do not block each other.
* **Rollback is honest.** It undoes, in reverse, only what the journal says was started, and reports `restored | partial | failed | not_needed` with what was undone, what could **not** be undone and why, and what is outside its scope (the tool's user data). It removes a version folder only if it still holds exactly what the transaction wrote; a receipt of a transaction that did not commit is removed first. A rollback that fails leaves the lock and the journal in `rollback_failed`; the next `recover()` retries.
* **Crash recovery** (`recover()`, run before new work): in-flight journals are rolled back, or **rolled forward** when the receipt is on disk and the described state is in place; a journal that fails its own digest is reported `CorruptJournal` and nothing is guessed or deleted; a lock without any journal (crash right after locking) is removed; leftover temporary files are cleaned.
* **Faults.** 18 injection points (failure or simulated process death) cover every step of install/update/uninstall and of rollback itself.

## 5. Tests (synthetic fixtures only)

* Recipes: the registry is empty and no real entry resolves a recipe; dozens of distinct validation refusals; review bound to content; strict deserialization; a validated recipe yields a complete draft whose only blocker is `user_approval_missing`; forged recipe status in a serialized plan is refused.
* Approvals: creation refusals (confirmation, actor, lifetime, action/source version, blocked plan, wrong recipe/platform, unknown project); every field edited with and without a recomputed binding; expiry boundaries; recipe/permission/plan/prerequisite changes; actions, computers and platforms do not cross; production accepts no actor.
* Lifecycle: install/update/uninstall; idempotent repeats; corrupted/truncated/extended/other-version/header-less artifacts; wrong platform; authority checks; failure at each of 12 install points and each update point with an exact restoration (byte-identical pointer); failed uninstall; honest rollback failures (`partial`, `failed`), lock retained and later recovery; crash at each point + restart + recovery (roll back or forward), idempotent recovery; orphan locks, corrupt journals, stray temp files; concurrency; confinement (hostile component names, junction/symlink-replaced sandbox folders with an outside canary, sandbox adoption); other account names and roots (`Ayşe Çelik`, nested, spaces) and no path/account name inside any managed file; restart/reopen; a tampered receipt; blocked writes (read-only pointer on Windows, `chmod` on Unix); inaccessible layout; no process / network / environment API in the production sources; no command, permission or build entry mentions the engine; process environment and working directory unchanged.
* Python (`tests/test_phase3a_lifecycle_contract.py`): the built binary's synthetic lifecycle is validated against `reviewed-recipe.schema.json` and `lifecycle-receipt.schema.json`; recipe, plan and receipt digests are recomputed independently; the story (install → repeat → update → failed update rolled back → crashed update recovered → uninstall) is asserted; nothing is created next to the sandbox.
* Mutations that each fail tests: path validation off (2), approval ignoring a changed plan (2), rollback always claiming success (5), changed-after-review accepted (1), positive evidence without provenance (3).

## 6. Interface

The existing "Kurulum Planı" page gains a section "Tarif ve onay durumu": whether a reviewed recipe exists (none / invalid with plain-Turkish reasons / validated), that **the plan is a draft and there is no user approval** (a plan id is not an approval), and whether rollback is *absent*, *only designed* or *only simulated on synthetic directories* — never "verified". A plan built from a synthetic recipe carries a "SENTETİK DEMO" banner. Missing requirements are the blocker list; the basis of every prerequisite (current scan / no current evidence) was already shown. There is no install, update, uninstall, approve or execute control, and none of the engine is reachable from the interface.

## 7. Portability

The engine's tests run on Windows x64 (locally and in CI) and on macOS ARM64 (CI); neither result is evidence for the other. Platform-specific cases: Windows junction replacement and read-only pointer file; Unix symlink replacement and `chmod` on the state folder (skipped when running as root). macOS CI is not a macOS GUI test. Windows Smart App Control can intermittently block a freshly built unsigned test executable on the development machine (`os error 4551`); this is handled by retrying, never by changing the setting, and release builds are verified in CI only.

## 8. Limits and what is next

* Approvals are in-memory objects: no persistence, no database table, no migration (data and audit chain untouched). A real flow needs persistence, a real confirmation control and an audit event design.
* The engine knows a single artifact form (one exact file). Archives need an authenticated inner-file digest or a reviewed extraction design.
* No process detection: updating/removing a file that is in use is not handled (see the Gitleaks assessment).
* Rollback of a *committed* transaction (as opposed to a failed or interrupted one) is not implemented.
* A hash is not a signature. See [GITLEAKS-PILOT-ASSESSMENT.md](GITLEAKS-PILOT-ASSESSMENT.md) for why even the simplest real candidate is not eligible yet.
