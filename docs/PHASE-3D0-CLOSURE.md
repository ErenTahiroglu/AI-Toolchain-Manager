## RT-3D0-02 — the custom verifier is supporting evidence, not the trust anchor

* `tools/verify_sigstore_bundle.py` stays (28 checks, negative tests) and is documented as **supporting evidence**; it checks the certificate chain signatures against a supplied root but does not implement the full X.509 profile/path validation or the trust-root rotation and revocation semantics of maintained verifiers.
* **The authority is the maintained GitHub CLI.** Installed version reviewed: **2.101.0**; supported flags read from `gh attestation verify --help`. Exact policy in [REQUEST-A.md](phase-3d0/REQUEST-A.md) §3 step 4: `--repo jqlang/jq`, `--cert-identity https://github.com/jqlang/jq/.github/workflows/ci.yml@refs/tags/jq-1.8.2`, `--cert-oidc-issuer https://token.actions.githubusercontent.com`, `--source-ref refs/tags/jq-1.8.2`, `--source-digest` and `--signer-digest 34f7186b86743a083a589741b6cea95293524108`, `--deny-self-hosted-runners`, `--predicate-type https://slsa.dev/provenance/v1`, `--hostname github.com`, `--format json`. Tested on a decoy file with the stored bundle and root: the flags are accepted together, the verification **fails closed** (exit 1) and no API request is made on the offline path. Learned in the test: `--cert-identity` and `--signer-workflow` are mutually exclusive, so the stricter exact-identity form (which contains workflow path and ref) is used. `--no-public-good` is deliberately not used (the certificate is from the Sigstore public-good Fulcio). The repository id (5101141), owner id (104800540) and the exact artifact name/size/digest are enforced after the CLI succeeds, by the reviewer, from its structured JSON and from the raw certificate (supporting verifier).
* **Trusted root:** the stored `sigstore-trusted-root.jsonl` is an evidence snapshot and is **not** treated as authenticated because its digest is written in this repository; the session obtains a fresh root through the CLI's TUF client (`gh attestation trusted-root`) for the supporting verifier and for the offline replay.
* **Disagreement fails closed.** `tools/review_jq_verification.py` (no network, runs nothing) reads the session outputs and passes only if: both files have the pinned size and SHA-256 and appear in the pinned checksum list and have no execute permission; the official verifier exited 0 **twice** (online, and offline replay with the stored bundle and fresh root) with a non-empty structured result whose subject, predicate type, log timestamp and every certificate field the CLI prints equal the pins; the supporting verifier passed all 28 checks **including the downloaded bytes**; **both verifiers agree** (a pass on one and a failure on the other fails the session, tested in both directions); each file has exactly one valid GPG signature by the pinned fingerprint (signing and primary key), no bad/expired/revoked/errored signature, and the isolated keyring holds exactly one certificate; every download hop was `https` on the allowed list.
* Three separate things are tracked and none is merged into another: **(1)** cryptographic provenance (official verifier + supporting verifier), **(2)** exact-file digest match on the downloaded bytes (size, SHA-256, publisher checksum list), **(3)** local code-signature facts (Authenticode status, PE/Mach-O header — recorded statically). Code-signature uncertainty is never mixed with Sigstore provenance. The jq pilot gates also remain: Issue #14 real-device evidence, the notice/licence review of Oniguruma and the Windows runtime, Smart App Control and Gatekeeper behaviour.
* The positive path of the official verifier could not be exercised before real bytes exist (a decoy cannot match a digest); its first real run is the Red Team's check on this procedure, and a mismatch in how the CLI names its JSON fields fails closed (reported, not trusted) — certificate fields the CLI prints are compared when present and reported when absent, while identity is also enforced by the CLI's own flags and by the raw-certificate verifier.
* Nothing creates or promotes an authenticated reference or `identity_verified`; promotion remains a separate reviewed code change after the Red Team has accepted the session evidence.
