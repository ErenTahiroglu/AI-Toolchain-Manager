## RT-3C-01 — atomic no-clobber on macOS

**Root cause.** `managed_fs_unix.rs::rename_file` checked that the destination did not exist and then called plain `renameat`, which atomically *replaces* an existing destination. A file created in the gap between the check and the call was overwritten even though the caller said "do not replace". The `replace=true` flag was also a general overwrite switch.

**Correction.**

* The generic `rename_file(.., replace: bool, ..)` **no longer exists**. There are two operations only:
  * `Dir::move_file(from, to_dir, to, expect_src)` — **no-clobber**: anything at the destination (file, folder, link, special entry) is refused with `Exists`. On macOS the refusal is made by the operating system atomically with the move: `renameatx_np(.., RENAME_EXCL)`. Windows already used `FileRenameInformationEx` without the replace flag (`STATUS_OBJECT_NAME_COLLISION`). If the primitive or the file system does not support it (`ENOTSUP`/`ENOSYS`/`EINVAL`) the result is `Unsupported`; **there is no fallback to `renameat`** (a test scans the source for `libc::renameat(`). After the move the file at the destination is re-identified; if the source name had been swapped in the gap the moved file is moved back (again with `RENAME_EXCL`) and the call fails with `Changed`.
  * `Dir::replace_owned_file(from, to_dir, to, src, dest)` — replaces **one specific, already-known file**: the destination must be a plain single-link file with exactly the identity `dest`, the file moved in must have the identity `src`. macOS uses `RENAME_SWAP` (atomic exchange), then verifies what was displaced and what moved in and **swaps back** if either is not as expected; the displaced old file is then removed by verified deletion (`DisplacedKept` if that fails). Windows verifies the destination through a handle opened without following links immediately before the replacing rename.
* Callers: replacement is used in exactly three places, all transaction-owned state transitions — writing the journal (replaces the journal file this transaction last wrote or read), the pointer switch of an **update** (replaces the pointer recorded as active when the transaction began; a fresh install uses the no-clobber move), and the pointer restore of a rollback (replaces the pointer this transaction wrote). A test asserts that the adapter source contains exactly three `replace_owned_file` calls and no `rename_file`. Every other move (staging, activation of the version folder, uninstall moves and undo) is no-clobber.
* Handle-relative confinement, source-identity verification, mount (`CrossDevice`) checks and the filesystem/link checks are unchanged and apply to both operations.

**API contract (sources and limits).** The macOS manual page of `rename(2)` (mirror: <https://keith.github.io/xcode-man-pages/rename.2.html>) documents `renameatx_np(fromfd, from, tofd, to, flags)`; `RENAME_EXCL` makes the call fail with `EEXIST` if the destination exists; `RENAME_SWAP` exchanges source and target in a single step (the two may differ in type, and `ENOENT` is returned if the target does not exist); both are "only on file systems that support" them (queryable through `VOL_CAP_INT_RENAME_EXCL` / `VOL_CAP_INT_RENAME_SWAP` in `getattrlist(2)`); an unsupported value yields `ENOTSUP`; combining the two yields `EINVAL`. **The page does not state the first macOS release that has these calls**; they have existed since the 10.12 era in the system headers (unverified here — to be confirmed against the SDK header availability annotations on the macOS test device). The application does not set a minimum system version of its own, so an older system without the symbol would fail to load rather than fall back (documented, not mitigated). The `libc` crate (0.2.191) declares `renameatx_np`, `RENAME_EXCL` and `RENAME_SWAP`. Which volume types support them was **not** established beyond the CI runner's APFS; every other file system is expected to return `ENOTSUP` and therefore to be refused.

**Evidence.** Behavioural tests that run on both platforms (Windows locally and in CI; macOS ARM64 in CI): destination exists before; destination created *in the gap* (hook between the preliminary check and the primitive) as a file, as a folder with nested data and as a symlink — each stays byte-identical, the source is intact, and the same move works after the owner resolved it; target holding unrelated user data; target a symlink (not followed, not removed); target a folder; source identity different (nothing moves); source swapped in the gap (macOS: the alien is put back, nothing lands at the destination; Windows: the pinned original is moved and the newcomer is untouched); source and destination on different volumes (simulated); legitimate no-clobber move succeeds and keeps the identity; repeated retries never overwrite; legitimate replacement succeeds and leaves nothing under the source name; replacement refuses another identity, a missing destination, a hard-linked destination, a folder and a link; a destination swapped in the gap before a replacement is swapped back, byte-identical (macOS). Mutation check: letting the no-clobber path use the replace flag fails the no-clobber tests.

**Residual, disclosed.** On **Windows** a replacement cannot pin the destination against deletion and replace it at the same time (tried: the replacing rename fails with a sharing violation when the destination is open without delete sharing), so a file created at the transaction-owned name in the instant between the identity check and the rename can be replaced; the test records this window instead of hiding it (it applies to the journal name, the active pointer name, only inside the owner-only managed folder). On macOS the swap-verify-undo sequence leaves a short period during which the alien object sits at the source name before it is swapped back; a crash exactly then leaves it there (reported as an unrecognised leftover, never deleted).

## RT-3C-02 — "already installed" without looking at the installed file

**Root cause.** `preflight_apply` returned `already_applied` when the pointer's version and digest matched the request and a self-consistent receipt (digest of itself) existed. The installed `artifact.bin` was never opened, so a deleted, truncated, modified, replaced or link-substituted artifact still produced a successful no-op.

**Correction (`verify_installed`, read-only).** `already_applied` is returned only when all of the following hold, otherwise the request is **refused with a deterministic code and nothing is touched** (no repair, no overwrite, no deletion, no adoption, no reinstall, no audit event, no approval consumed, no journal or file created):

1. pointer ↔ request: same tool, version and digest (`installed_state_pointer_mismatch`);
2. receipt ↔ pointer: the receipt named by the pointer exists and its own digest matches (`installed_state_has_no_valid_receipt`), and it binds to the same transaction, tool, version, artifact digest, platform, computer, state `committed` and action install/update (`installed_state_receipt_mismatch`);
3. the version folder exists (`installed_artifact_missing` — absence is distinguished from drift) and is a real folder, not a link (`installed_artifact_drift`);
4. it holds `artifact.bin` as a regular file (a link or folder under that name is `installed_artifact_drift`; absence is `installed_artifact_missing`) and **nothing else** (`installed_folder_has_unexpected_entries`);
5. the file, opened through a confined no-follow handle, has exactly one link, the recipe's size and the recorded SHA-256 (`installed_artifact_drift`);
6. its file identity equals the identity recorded in the installing transaction's journal (`installed_artifact_drift`; if that journal or entry is gone: `installed_identity_unprovable`).

**What can and cannot be proven after a restart.** Provable: kind, link count, size and digest through the confined handle; the identity the installing transaction recorded (volume + file index on Windows; on macOS only the inode, because device numbers are not stable across mounts). Not provable: that the journal itself is genuine (it is unauthenticated evidence — a same-user process can forge it) and, above all, that the artifact is the publisher's: nothing here is labelled `identity_verified`; that remains the sole job of the authenticated reference set, which is empty. Messages carry fixed codes only — no absolute path, no account name, no artifact content (tested).

**Evidence.** Correct install and repeated identical request (no new journal, file, folder, audit record, or consumed approval); artifact deleted (and the version folder, and the tool folder); same-size content modified in place; different size; identical bytes in a different file; hard-linked alias; file symlink and folder junction/symlink substitution (targets untouched); unexpected second file and folder; pointer naming another tool; stale receipt (pointer ↔ receipt of another transaction); forged receipts with a valid digest but wrong tool, version, platform, computer, action or artifact; altered receipt digest; missing receipt; missing journal; no path or content in messages. Mutation checks: removing the identity comparison, the sibling check or the whole verification each fail tests.
