# CATALOG-03 — handoff to PRODUCT-07 (not started)

Nothing in this phase starts PRODUCT-07. The next planned step is **PRODUCT-07, [Issue #29](https://github.com/ErenTahiroglu/AI-Toolchain-Manager/issues/29)**: "decide provenance-aware evidence selection without false project installation claims". It begins with a **bounded evidence-selection policy proposal** that goes to independent Red Team / product approval *before* any Rust selection code changes. No migration or IPC change without a separate reviewed decision.

## Why the catalog is the wrong place to fix it
`classify_request` still lets the best *current* answer win by presence rank and then by newest id, whatever its scope (PRODUCT-06 only *discloses* where the winner came from). A computer-wide `present` can therefore outrank a project-specific `absent`; neither proves what the project has configured. That is a selection-policy question, independent of how many candidates the catalog lists. CATALOG-03 does not touch it: no scanner, detector, observation or classification was added or changed, and a stored scan says nothing about any of the four new tools.

## Facts from CATALOG-03 that PRODUCT-07 should have in front of it
* **Catalog now has 22 candidates; none is a tested tool.** The only declared compatibility cell among the four new entries is Claude-Mem × Claude Code × Windows, on a quarantined, blocked-until-scoped-authorization entry — it can never permit "kullanmak istiyorum". Every other cell is `unknown`. The application therefore still has no entry among the four that a user could even *wish* for, except through "Şimdi değil" / "Reddet". This is the existing rule working, and it is the reason a **wish of interest** ("ilgileniyorum" / "değerlendirilecek") that is *not* an acceptance is worth designing separately (the C02 follow-up listed in the PRODUCT-07 brief): it must never become a compatibility acceptance or an install authorization, and unknown must not be relabelled vendor-declared to make it available.
* **Detection has nothing to match yet.** None of the four has a discovery detector. Before any of them could appear in a scan, someone must decide *what* is observed (a binary, a plugin record in an agent configuration, a hook entry, a data folder such as `.ua/`, `~/.claude-mem/`, `.claude-flow/`) — and each of those is a project-specific or computer-wide fact with a different scope, which is exactly the PRODUCT-07 question. Several of the four would also leave **project-local** state (`.ua/`, `.claude-flow/`, `CLAUDE.md`), which is project-specific evidence by nature, while their binaries and user-profile folders are computer-wide.
* **Hooks are the cross-cutting hazard.** Three of the four can install or inject hook-like behaviour on the same agent events. Any future evidence model (and any future agent-configuration management) will need to *enumerate hooks per agent and per project* before it can say anything honest about combinations; the application cannot do that today.
* **Identity discrepancies are data, not noise.** The Karpathy-inspired repository's canonical owner differs from the owner its own manifests name; Ruflo's root package is named `claude-flow` while its README offers `ruflo`. A detector or an installer keyed on a package or owner name would inherit these ambiguities; a source-identity rule belongs in the policy, not in a heuristic.
* **Quality gate state.** The description-quality gate (CATALOG-02) now lists twelve known gaps: the eleven older entries and the documented, justified licence exception of the Karpathy-inspired entry. They are backlog items for a future catalog pass, not blockers.

## What the policy proposal should therefore cover (suggested, not decided)
1. A static map of the existing classifier, relevance filters, ranking and origin contract, with exact code and test references.
2. A deterministic synthetic comparison grid: four-field identity × project-specific vs computer-wide × exact surface vs `local-cli` fallback × present/absent × current/old × conflicting evidence × missing scans.
3. Options: keep the rank with a mixed-evidence notice; prefer project-specific evidence under stated conditions; or introduce an explicit ambiguous/conflict status — with backward compatibility for the matrix and the review queue.
4. A separate design for a non-binding "interested" state.
5. One proposal, submitted for independent approval before any implementation.

## Boundaries that stay in force
REAL_INSTALLATION_NO_GO. Issues #14 (filesystem TOCTOU) and #25 (WebView2 egress / profile isolation) stay open. The Rev 5 / offline-preflight harness, the jq pilot and any real GUI test stay deferred; `main` stays frozen at `68eda3f0407490fabccb517dcf822ab4818fc0bf`. Green CI is not evidence of a safe production runtime. After the policy decision the product returns to real end-product gaps — a safe, isolated agent-configuration management model, the installation gates, controlled-environment GUI tests, and only then scoped install / update / remove / rollback and sync — not to another round of read-only additions.
